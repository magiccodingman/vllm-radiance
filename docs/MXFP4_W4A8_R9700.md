# MXFP4/W4A8 on dual Radeon AI PRO R9700

## Scope and provenance

This continuation ports the native gfx1201 MXFP4 work from
[`ggz14/radiance-vllm-mxfp4`](https://codeberg.org/ggz14/radiance-vllm-mxfp4),
source branch commit `3636713c8bfbf216c9265db352f10faed515156f`, including merged-main
decode-fusion commit `e72bca1fb3b77fe50bef34c96033cd812db80f73`, onto this fork's existing
vLLM 0.27.1, AMD Torch 2.12, AMD Triton 3.7.1, AITER 0.1.20, ROCm 7.14,
R4D, FP8, MTP, and DFlash2 stack. The MXFP4 integration and HIP kernels were
authored by Brian in that public branch; this port preserves attribution while
adapting its guarded patches, image build, Compose contract, and benchmark lab.

libr4d is pinned to `b9e42ab7202f53a3bc13d415f5d41481f9ca311b`, a post-v0.4.0
commit containing the GDN exponent-overflow guards required by this target. The
extension still reports `0.4.0` because those fixes have not received a new tag.
Without the guards, non-finite GDN activations poison per-token FP8 scaling and
the W4A8 model can become fluent-looking garbage.

## Model contract

The qualification checkpoint is
[`amd/Qwen3.8-27B-Quark-AWQ-MXFP4`](https://huggingface.co/amd/Qwen3.8-27B-Quark-AWQ-MXFP4).
It is a 64-layer `Qwen3_5ForConditionalGeneration` checkpoint with packed OCP
E2M1 MXFP4 group-32 target weights, dynamic MXFP4 activations in its declared
Quark recipe, BF16 vision linears and `lm_head`, a 262,144-token architecture
limit, and an embedded one-layer MTP head. The downloaded safetensors payload is
18.44 GiB. Exact local file hashes and the image digest are retained in the run
manifests; the publication report records them again after final qualification.

The deployment target retains FP8 KV. BF16 KV may be useful as a diagnostic, but
it is not silently substituted in any published performance lane.

AMD's model card reports 94.996% flexible-extract / 95.30% strict-match GSM8K
in the thinking profile versus 93.33% / 93.33% for its BF16 base, and 89.92% /
89.76% non-thinking versus 90.67% / 89.76% for BF16. Those upstream results are
useful evidence that the AWQ checkpoint itself retained its reasoning ability;
our gates separately test this serving implementation and do not relabel AMD's
evaluation as a Radiance result.

## Implementation

Stock vLLM treats gfx1201 as lacking native MXFP4 and selects emulation. The
ported integration adds two explicitly gated routes:

1. `RADIANCE_MXFP4=1` allows AITER's Triton `gemm_afp4wfp4` implementation on
   gfx1201 and installs measured WMMA-16 tile tables. This is a diagnostic/native
   W4A4 route; it does not use RDNA4 FP8 WMMA.
2. `RADIANCE_MXFP4_W4A8=1` registers `RadianceMxfp4W4A8LinearKernel` ahead of the
   ROCm MXFP4 plugins. It consumes packed MXFP4 weights, quantizes activations per
   token to FP8 E4M3, and launches a hand-written gfx1201 FP8-WMMA HIP extension.

The production W4A8 route has two tilings. `M<=48` uses a decode-shaped split-K
kernel with no 256-row waste; its final arriving block now performs the reduction
in place, removing a second HIP launch per linear. Larger M uses the prefill tile,
switching to TN=4 from M=2048. The folded exponent table extends through E4M3
subnormals: values are exact through exponent delta 8 and rare deltas 9–12 round
instead of flushing entire weight groups to zero. The source author measured the
change eliminating all `>2%` CHECKALL failures and improving WikiText-2 perplexity
from 8.3736 to 8.3719 without a measurable speed cost. All 304 target linears must
select this kernel on both TP ranks.

`RADIANCE_MXFP4_W4A8_MIN_M=0` is a correctness requirement. AITER's generic
W4A4 fallback produces a wrong result for the Qwen GDN `N=5120,K=3072`
projection. The benchmark harness refuses to publish a purported qualified
MXFP4 run with a nonzero minimum.

The port also restores `RADIANCE_AR_MAX_KB` and
`RADIANCE_AR_QUANT_MIN_KB` as real runtime controls. The all-reduce ceiling must
cover `max_num_batched_tokens * hidden_size * 2` bytes or large prefill messages
silently return to RCCL. The portable 4,096-token, hidden-size-5,120 profile fits
under the unchanged 48 MiB default; an 8,192-token chunk requires a larger
explicit ceiling.

## Runtime profile

```dotenv
WEIGHT_QUANTIZATION=auto
RADIANCE_MXFP4=1
RADIANCE_MXFP4_W4A8=1
RADIANCE_MXFP4_W4A8_MIN_M=0
RADIANCE_MXFP4_DECODE_MAX_M=48
RADIANCE_MXFP4_TN4_MIN_M=2048
RADIANCE_AR_MAX_KB=49152
# MTP only: AMD's embedded MTP tensors are BF16, not packed Quark FP4.
RADIANCE_QUARK_BF16_MTP=1
```

Normal Compose defaults remain native FP8 and non-speculative so existing users
do not silently change target numerics. MXFP4 is a checkpoint profile, not an
optimization to enable over an FP8 checkpoint. MTP and DFlash2 remain separate
speculative choices layered above the selected target engine.

AMD's metadata applies the global Quark recipe to every unexcluded linear even
though all 15 embedded `mtp.*` tensors are BF16. Unpatched vLLM therefore creates
packed MTP parameters and fails its weight-shape assertion during load. The
guarded `RADIANCE_QUARK_BF16_MTP=1` compatibility path constructs only that MTP
submodule unquantized; it does not alter the MXFP4/W4A8 target engine. It stays
off by default because a future checkpoint may contain genuinely packed MTP.

Stable vLLM 0.27.1 contains the older Qwen DFlash runtime, not the Qwen3.8
`DFlash2DraftModel` local-convolution/candidate-selector implementation. This
fork selectively backports upstream vLLM PR #52816 at exact head
`3406ec1dae9916f920b90f0dbf90dcf54923d042` instead of floating the entire vLLM
dependency. The matching `tcclaviger/Qwen3.8-27B-DFlash2-FP8` checkpoint also
exposed an upstream raw-quantized-weight bug: context precompute concatenated FP8
K/V slices and called `F.linear` without applying their block scales. Radiance
materializes only those small fused context-K/V slices in BF16; ordinary draft
linears remain FP8. The failed architecture-alias, legacy-loader, and unscaled-FP8
attempts remain preserved as negative evidence.

## Long-context and prefix-cache production checkpoint

The published image was additionally qualified at 90% GPU allocation with the
target-matched DFlash K5 drafter. The prefix-disabled all-GPU sweep completed
32K C11, 64K C7, 128K C4, and 256K C2; conservative operating suggestions are
32K C8, 64K C6, 128K C4, and 256K C2. Minimum observed physical headroom across
that matrix was 5.06 GiB per GPU.

The recommended production profile instead preserves automatic prefix caching:
128K C4, `--enable-prefix-caching`, and `--mamba-cache-mode=align`. It exposed
576,001 KV tokens / 4.39x full-request capacity and completed four disjoint
130,816+256-token requests with no OOM or preemption and 5.17 GiB minimum
headroom. A deterministic 32K cold/warm comparison reduced TTFT from 9.036
seconds to 0.705/0.707 seconds (12.8x), reused 93.7% of the prompt, and produced
byte-identical sequential outputs. See
[COMPOSE_CAPACITY.md](COMPOSE_CAPACITY.md) for the full matrix, serving TPS,
telemetry, and the distinction between cold maximum capacity and the recommended
cached profile.

### Negative and diagnostic results retained

- Native AITER W4A4 is not a safe fallback for this checkpoint: the GDN
  `N=5120,K=3072` projection is wrong. Qualified W4A8 must cover M=0 upward.
- Stock libr4d v0.4.0 allowed exponent overflow to create non-finite GDN state;
  fixed source `b9e42ab` is required.
- Stable vLLM 0.27.1 rejected the Qwen3.8 DFlash2 architecture until the exact
  PR #52816 backport was applied.
- The first selective-FP8 DFlash2 load reached a raw FP8 `F.linear` in context
  K/V precompute. Applying the recorded block scales to only those fused K/V
  slices fixed it while keeping ordinary draft linears quantized.
- R4D GDN deliberately falls back for mixed prefill/decode steps (observed at
  c8); requests remained correct and completed. This is a future optimization
  opportunity, not a hidden benchmark failure.
- DFlash reserves speculative scheduler slots: the 4,096 CLI budget becomes
  4,064 target slots for K5 and 4,048 for K7. MTP retains 4,096. The tiny
  distinction is recorded rather than silently increasing unlike CLI budgets.

## Safety rules

- Do not call the W4A8 path bit-identical to W4A4 emulation; FP8 activations are
  more precise but numerically different.
- Do not publish AITER-fallback whole-model results as qualified for this Qwen
  checkpoint; the missing `o_proj` tune is a correctness failure.
- Do not run against stock libr4d v0.4.0 without either the fixed commit or an
  explicitly labeled activation-sanitizer diagnostic.
- Do not compare cold JIT startup against hot inference.
- Do not combine MTP and DFlash configurations. A DFlash drafter trained for a
  different target is only a compatibility experiment, not a qualified lane.
- Preserve the existing FP8 dispatcher and DFlash paths; the MXFP4 switches are
  isolated and off by default for non-Quark models.
